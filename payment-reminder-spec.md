# Техническое задание: Payment Reminder Backend

> **Статус документа:** исходное историческое ТЗ. Оно фиксирует требования и ограничения на момент старта, но не является актуальным руководством по запуску или полным описанием реализованной системы. Текущее поведение описано в `README.md` и `payment-reminder-design.md`.
>
> После согласования ТЗ проект был расширен: добавлены Dockerfile и полный Docker Compose стек, `currentPeriodId` и календарные anchor-поля, валюта в истории, персистентные notification jobs и polling offset, а также Telegram-меню и мастер с таблицей `telegram_conversations`. Поэтому запрет Docker в разделе 21 и инструкция агенту «только анализировать» в разделе 25 сохранены исключительно как история первоначальной постановки.

## 1. Цель

Реализовать backend-сервис **Payment Reminder** для управления
регулярными ручными платежами.

Пользователь должен иметь возможность:

-   создавать регулярные платежи;
-   просматривать их;
-   редактировать;
-   деактивировать;
-   задавать несколько сроков напоминания;
-   получать уведомления в Telegram о приближающихся платежах;
-   отмечать платеж как оплаченный;
-   хранить историю совершённых платежей;
-   переносить напоминание на следующий день.

Все платежи считаются **ручными**.

Сервис не выполняет банковские операции и не интегрируется с банковскими
счетами.

`paymentUrl` и другие ссылки для оплаты не использовать.

## 4. Основная сущность Payment

Регулярный платёж.

Поля:

``` text
id
name
amount
currency
recurrence
nextPaymentDate
active
createdAt
updatedAt
```

### id

Уникальный идентификатор.

### name

Название платежа. Обязательное поле.

Примеры:

``` text
Ипотека
Интернет
Мобильная связь
ОСАГО
```

### amount

Сумма платежа.

Использовать `BigDecimal`.

Не использовать `double` или `float`.

Значение должно быть больше нуля.

### currency

Валюта.

На первом этапе достаточно:

``` text
RUB
USD
EUR
```

Реализовать enum.

### recurrence

Периодичность платежа.

MVP должен поддерживать:

``` text
MONTHLY
YEARLY
```

Архитектура должна позволять позже добавить другие варианты без
изменения существующих данных.

### nextPaymentDate

Дата следующего ожидаемого платежа.

Использовать `LocalDate`.

### active

Позволяет временно отключить платеж без удаления истории.

## 5. PaymentReminder

Один Payment может иметь несколько правил напоминаний.

Например:

``` text
Ипотека

за 5 дней
за 3 дня
за 1 день
```

Сущность:

``` text
id
paymentId
daysBefore
```

Ограничение:

``` text
daysBefore >= 0
```

Не допускать одинаковых `daysBefore` для одного Payment.

Например:

``` text
payment_id = 10
days_before = 3
```

означает: отправить напоминание за 3 дня до `nextPaymentDate`.

------------------------------------------------------------------------

## 6. PaymentHistory

Хранит историю фактически отмеченных пользователем оплат.

Поля:

``` text
id
paymentId
scheduledDate
paidAt
amount
```

Где:

-   `scheduledDate` --- дата, когда платеж должен был быть выполнен;
-   `paidAt` --- фактическое время, когда пользователь отметил его как
    оплаченный;
-   `amount` --- сумма платежа на момент оплаты.

Изменение `Payment.amount` в будущем не должно менять исторические
записи.

------------------------------------------------------------------------

## 7. REST API

### Создание платежа

``` http
POST /api/payments
```

Пример:

``` json
{
  "name": "Ипотека",
  "amount": 35300.00,
  "currency": "RUB",
  "recurrence": "MONTHLY",
  "nextPaymentDate": "2026-09-25",
  "reminders": [5, 3, 1]
}
```

### Получение платежей

``` http
GET /api/payments
```

По умолчанию вернуть активные платежи.

### Получение платежа

``` http
GET /api/payments/{id}
```

### Изменение платежа

``` http
PUT /api/payments/{id}
```

Должна существовать возможность изменить:

-   name;
-   amount;
-   currency;
-   recurrence;
-   nextPaymentDate;
-   reminders;
-   active.

### Деактивация

``` http
PATCH /api/payments/{id}/deactivate
```

Не удалять `PaymentHistory`.

## 8. Отметка платежа как оплаченного

Endpoint:

``` http
POST /api/payments/{id}/pay
```

При выполнении операции необходимо в рамках одной транзакции:

1.  Получить Payment.
2.  Проверить, что платеж активен.
3.  Запомнить текущий `nextPaymentDate`.
4.  Создать запись PaymentHistory.
5.  Сохранить текущую сумму Payment в PaymentHistory.
6.  Рассчитать следующую дату платежа.
7.  Обновить `nextPaymentDate`.

Для `MONTHLY`:

``` text
25.09.2026
→
25.10.2026
```

Для `YEARLY`:

``` text
15.03.2026
→
15.03.2027
```

Корректно обрабатывать календарные даты.

Например, месячный платеж 31 числа не должен приводить к ошибке в
феврале.

## 11. Формат Telegram-уведомления

Пример:

``` text
💳 Предстоящий платеж

Ипотека
35 300 ₽

Дата платежа: 25 сентября 2026
Осталось: 3 дня
```

``` text
✅ Оплачено
⏰ Напомнить завтра
```

Кнопка `Оплачено` должна инициировать ту же бизнес-операцию, что:

``` http
POST /api/payments/{id}/pay
```

Не дублировать бизнес-логику Telegram-кодом.

## 12. Scheduler

Реализовать периодическую проверку платежей.

Scheduler должен находить платежи, для которых:

``` text
nextPaymentDate - currentDate == daysBefore
```

для одного из `PaymentReminder`.

После нахождения отправлять Telegram notification.

Период запуска scheduler должен задаваться конфигурацией, а не быть
жестко зашит в код.

------------------------------------------------------------------------

## 13. Защита от повторных уведомлений

Необходимо гарантировать, что один reminder для одного платежного
периода не будет отправляться повторно при каждом запуске scheduler.

Например:

``` text
Payment: Ипотека
scheduledDate: 25.09.2026
daysBefore: 3
```

должен породить максимум одно обычное уведомление за 3 дня.

Способ реализации выбрать самостоятельно, но состояние отправленных
уведомлений должно храниться в PostgreSQL.

Не полагаться только на память JVM.

------------------------------------------------------------------------

## 14. «Напомнить завтра»

При нажатии:

``` text
⏰ Напомнить завтра
```

создать отложенное дополнительное напоминание.

Оно должно переживать:

-   restart приложения;
-   redeploy;
-   restart pod в будущем.

Поэтому состояние также должно храниться в PostgreSQL.

------------------------------------------------------------------------

## 15. Просроченные платежи

Если:

``` text
currentDate > nextPaymentDate
```

и платеж не был отмечен как оплаченный, он считается просроченным.

Отправлять Telegram-уведомление:

``` text
🔴 Просроченный платеж

Ипотека
35 300 ₽

Дата платежа: 25 сентября
Просрочено: 1 день

[✅ Оплачено]
[⏰ Напомнить завтра]
```

Не отправлять просроченное уведомление чаще одного раза в сутки.

## 16. PostgreSQL

Hibernate не должен самостоятельно создавать production-схему.

Использовать:

``` text

```

или эквивалентную конфигурацию.

Создать необходимые:

-   primary keys;
-   foreign keys;
-   unique constraints;
-   indexes.

Особое внимание уделить запросам scheduler по:

``` text
active
nextPaymentDate
```

## 23. Критерии готовности MVP

Работа считается завершённой, если можно выполнить полный сценарий:

``` text
Создать Payment
       ↓
Payment сохранён в PostgreSQL
       ↓
Scheduler обнаруживает дату reminder
       ↓
Telegram получает сообщение
       ↓
Пользователь нажимает "Оплачено"
       ↓
PaymentHistory создаётся
       ↓
nextPaymentDate пересчитывается
       ↓
старое уведомление больше не отправляется
```

Также должен работать сценарий:

``` text
Telegram reminder
       ↓
"Напомнить завтра"
       ↓
состояние сохраняется в PostgreSQL
       ↓
restart приложения
       ↓
на следующий день reminder всё равно отправляется
```
